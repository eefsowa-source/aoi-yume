# Workflow preferences

- Expects the agent to commit changes with a sensible, descriptive message and push the current branch to the remote at the end of each working session (requested repeatedly, ~10 times across sessions). Confidence: 0.95
- Prefers retrying failed operations ("다시 시도" / "try again") instead of stopping or switching approach when a command fails. Confidence: 0.8
- After applying file edits, verifies the changes actually landed by re-reading the file (or grepping for the expected tokens) before re-running the build — file edits have reported success without persisting (e.g., Sampler.h Voice class, Parameters.h env IDs, PluginEditor init list); recover by re-applying the same edit. Confidence: 0.85
- Treats a feature as "done" only after the full build is clean AND the test suite (e.g., `ctest`) passes — the user does not consider the work complete until both hold simultaneously. Confidence: 0.8
- Wants fast-paced development and quick iteration ("ok gonna develop more fast"), favoring steady shipping progress over slow deliberation. Confidence: 0.7
- Does not want the agent to use cloud-synced storage paths (e.g., the Dropbox/Eefsowa Samples folder) for test data; the user will provide file links or place files in a local testdata directory instead. Confidence: 0.9
- Prefers inspecting the existing build configuration (CMakePresets.json, existing build directories) before running a build, and reusing already-configured build trees rather than re-fetching dependencies from scratch. Confidence: 0.6
- Often runs multiple AI coding agents (e.g., Codex) on the same repository in parallel, and expects the agent to coordinate with the user to avoid editing the same files and to check git status before committing. Also expects the agent to review/inspect the other agent's work (diff, untracked outputs) to understand scope before acting — e.g., asked the agent to pick up and help with Codex's in-progress work ("코덱스가 하고있는일 도와줘"), which requires first investigating the other agent's uncommitted state and reporting status. Re-requested in a later session with "코덱스가 하고있는작업 보조", again prompting the agent to survey git status, running Codex processes, stashes, and branches to determine what (if anything) the other agent is actually working on before acting. Confidence: 0.9
- Interested in agent-to-agent orchestration: asked whether Command Code can be used as a subagent from Codex (i.e., invoking Command Code headlessly via CLI as a tool/subprocess of another agent), suggesting openness to wiring Command Code into external agent workflows. Confidence: 0.5
- Expects the agent to track and summarize pending/in-flight work across the repo and parallel agents (git status, uncommitted changes, milestone progress, unresolved issues) and proactively present a prioritized, actionable next-step list with an option order when asked what work remains — rather than the agent picking unilaterally. Confidence: 0.7
- Wants the agent to proactively survey the whole project and report improvement/debugging candidates (git refs/repo health via fsck, test suite results, recently changed code paths, sanitizer build availability) and present them as a prioritized list with a recommended order — asked both "지금 프로젝트 debug 해야할것들 찾아봐" and "지금 코드 훑어보고 개선해야할것 찾아봐", expecting a survey report before any fix. Reinforced again when "더 해야할건?" was answered with a state check (full build, git status, test coverage) plus a prioritized report including corrupted codex refs, per-block param-update optimization candidates, and test coverage gaps. Confidence: 0.8
- When deciding among options and unsure, asks the agent for its recommendation (e.g., "what u recommend" about which custom agents to create) and expects a prioritized shortlist with a clear default choice rather than the agent punting the decision back with open-ended questions; once a recommendation is given, replies with just "추천" to approve it — or echoes the proposed numbered order (e.g., "2-3-1-4" to approve the agent's fix sequence, or "1" to pick the first item of a prioritized todo list) — and expects the agent to proceed with that choice without further confirmation. Re-confirmed when the user replied "1" to pick the first recommended fix (release click) from a prioritized improvement list. Confidence: 0.95
- When the agent proposes a numbered multi-part plan, prefers running the independent parts in parallel rather than sequentially — e.g., replied "1.2.3 parrarel" to execute three proposed tasks concurrently. Confidence: 0.6
- Values keeping the git repository healthy and clean: approved cleaning corrupted codex refs (files with `Icon\r` names) that were poisoning `git fsck` and warning on every git command — investigating before deleting (identifying the files as empty 0-byte artifacts), preserving legitimate refs/objects, and verifying `git fsck` is clean afterward. Confidence: 0.65
- When preparing a commit with mixed content, prefers a clean, deliberate scope: commit only durable source/config (tests, agent definitions, analysis scripts) and exclude generated artifacts (PNG screenshots, CLI output dirs), deleting stray corrupted files (e.g., another `Icon\r` 0-byte file) found during staging rather than committing them. The agent's proposed split (include tests + `.commandcode/` + `outputs/*.py`, exclude `outputs/cli/` and PNGs) was approved by the user with a terse "커밋 ㅐ", and the follow-up wrap-up approved (via "마무리") adding `.gitignore` rules (`outputs/*.png`, `outputs/cli/`, `outputs/Icon?`) so generated artifacts stay out of git status entirely rather than being committed. Confidence: 0.7
- On a terse "마무리" (wrap up) to close out a session, expects the agent to autonomously finish everything without further confirmation questions: inspect remaining untracked files, classify durable vs throwaway (adding `.gitignore` rules for generated artifacts), commit remaining changes (including auto-updated taste/learning files), and verify a clean working tree before giving the final session summary. Confidence: 0.65
